## Почему IRSA отвечал 502 и что исправлено

Живая проверка показала различие сервисов, а не полную недоступность IRSA:

- Главная страница и `/TAP/availability` — HTTP 200, `available=true`.
- Простой GET к `TAP_SCHEMA.tables` — HTTP 200; POST того же запроса — HTTP 502,
  HTML `Proxy Error`, `Error reading from remote server`.
- GET к таблицам `spherex.plane`/`artifact` — 502 либо ReadTimeout; изменённый запрос
  по официальному примеру также не завершился за 50 секунд.
- Официальный `/SIA` для DR1 и QR3 — HTTP 200, `QUERY_STATUS=OK`, реальные наблюдения.
  Для Барнарда получено 59 уникальных экспозиций D3; новая FITS-вырезка открыта загрузчиком,
  `obs_id=2025W33_2C_0321_1`, размер 29×29, MJD UTC `60902.865380749`.

Это свидетельствует об отказе/задержке маршрута TAP к метаданным SPHEREx. Точную внутреннюю
причину на стороне IPAC без их журналов установить нельзя; смена локальных зависимостей
и бесконечные повторы одного POST её не исправляют.

Исправление приложения: один GET к TAP с таймаутом 12 секунд; при отказе — живой SIA2,
DR1 предпочтительнее дубликатов QR3. После отказа один процесс не пробует TAP следующие
300 секунд, затем проверяет восстановление. SIA-источник и ограничение свежести попадают
в API и предупреждения, сохраняются в кэше даже при пустой выборке. Ответы ERROR/OVERFLOW
не считаются успешным отсутствием покрытия. Прямые FITS-ссылки SIA больше не читаются как datalink XML.

SIA2 может отставать от TAP примерно на сутки для новых загрузок; это описано в
[официальном руководстве SPHEREx](https://caltech-ipac.github.io/spherex-archive-documentation/spherex-data-access/).
Поддержка GET подтверждается [документацией IRSA TAP](https://irsa.ipac.caltech.edu/docs/program_interface/TAP.html).
Отдельные HTTP 503 при создании вырезок остаются временными ответами архива; загрузчик
повторяет их и сохраняет успешно полученные FITS. Успех поиска не объявляется обнаружением звезды.
